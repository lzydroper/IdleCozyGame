# 概述

关卡是对战斗区域的进一步细化，当前区域被抽离成了三个概念：一个是探索的区域，一个是挂机战斗的区域，一个是挂机探索的区域

需要将它们整合到一起，具体为：

1. 修改探索功能当前每次进入只是在事件列表中随机找一个Event触发的现状，而是引入区域概念，进行分组，玩家应在探索前选择要探索的区域，根据区域来决定初始消耗而非目前的硬编码消耗；
2. 怪物配置统合进区域内，使得探索和战斗的敌人列表统一；
3. 探索是最先解锁区域的地方，只有探索中对某个区域的探索程度达到某个数值，才能在探索中解锁其他区域；该区域探索程度达到100%，才能在战斗中解锁（必要条件而非充分条件，可能还有别的条件），才能在挂机探索中解锁

然后要清理战斗事件的冗余，扣除体力不是战斗事件该负责的，而是触发战斗事件的事件该负责申请，并由体力系统审核的；

区域内会有多个关卡，每个关卡内有怪物配置，在底层实现上不区分boss关卡，仅在配置时选择在某个关卡加入敌人boss而已；

关卡的解锁仅与上一个关卡是否解锁有关，云端存档记录通过关卡的bitmask或id的list；

关卡负责记录战利品列表，并额外维护首次通关的特殊战利品（可空）；

经验等掉落不应该由怪物负责维护，而是由关卡维护，胜利就获得所有，失败就没有；

掉落配置应该将所有都统合为物品，不单独维护经验、灵魂残响等等物品，只记录id和两层重载：{int 数量}，{int 数量，int 概率（如概率为25表示25%出现掉落，一次掉落对应数量）}，还有可能是权重轮盘，即一个池子中多种物品根据权重仅选出一个，表现为[{id, cnt, per},{id, cnt, per},{id, cnt, per}]，表示必定从这三件物品中得到一个，根据权重分配哪一件概率最高；掉落的显示层概率需要显示为xx%，轮盘池子内配置 `weight`（纯权重整型），UI 显示时由代码动态计算 `(weight / totalWeight) * 100` 后格式化为百分比
