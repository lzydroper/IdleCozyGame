# Offline 模块「将就」待完善清单

> 记录范围：`combat-offline`（战斗离线暂停与体力解耦，对应 ADR-0020 与工单 01–05）实施后的**已知取舍与未闭环项**。  
> 实现基线：当前工作区（工单 01–05 全部验收通过，全量单测通过）。  
> 语义：本文件只记录「能跑通、但为了先落地而做出的妥协」，不是 bug 清单；已通过的构建与测试不代表这些点不需要后续打磨。  
> 关联留档：实体/回合/能力/效果/Buff 的「将就」清单见同目录 `Entity.md` / `Turn.md` / `Ability.md` / `Effect.md` / `Buff.md`；Offline 聚焦于离线暂停、体力解耦、在线挂机循环与持久化隔离。

---

## 1. 挂机战斗的在线事件流与 UI 播放器尚未对接（UI 仍是独立/轮询模拟）

- **现状**：`levelCombat.ts` 的 `settleLevelIdleUpdate` 是批量纯函数（按秒数计算战斗场次并一次性结算所有战斗），而 `IdleCombatWidget.tsx` 内部使用了一个 `setInterval` 循环和队列播放器，每个 interval 重新模拟一场战斗；在后台切换 tab 或离开战斗标签页时，UI 组件 unmount，实际依赖的是 `GameContext` 每秒 Tick 调用 `settleLevelIdleUpdate`。
- **妥协点**：为了优先保证纯函数状态机与离线暂停的正确性，UI 层的展示流与全局 Tick 存在双重模拟与节奏差异；挂机 UI 交互体验按 spec 明确由后续 `combat-ui` 专项负责。
- **待完善**：在 `combat-ui` 专项中统一挂机信息流的生产者与消费者模型，将事件流轻量广播或订阅播放，避免组件内独立模拟与全局 Tick 批量结算逻辑分叉。

---

## 2. 体力恢复仍挂在顶层 `GameState`，尚未与资源/属性体系完全统一

- **现状**：`stamina` 和 `maxStamina` 目前是 `GameState` 的顶层数值字段，`src/state/stamina.ts` 封装了 `getStamina`、`getMaxStamina`、`recoverStaminaByTime`、`tryConsumeStamina` 等纯函数服务。
- **妥协点**：虽然体力计算已彻底解耦为纯函数服务，但数据结构上仍散落在 `state.stamina`，而不是作为标准资源实体（如魔导资源或玩家属性）纳入统一资源管理或 modifier 体系（无法像 attack/defense 那样由装备/Buff/基建动态提供 `maxStamina` 或回复速度的公式加成）。
- **待完善**：后续若有「装备/天赋/建筑提升体力上限或体力回复速率」的需求，需在 `stamina.ts` 中接入 `statSystem` / `modifier` 计算，扩展 `getMaxStamina(state)` 与 `getStaminaRegenRate(state)`。

---

## 3. 挂机秒数累积上限仅依赖自然体力，无显式在线时间截断

- **现状**：按 ADR-0020 清理了旧的 `COMBAT_CONFIG.maxIdleSettlementSeconds`（原 8 小时离线结算上限），在线状态下 `accumulatedSeconds` 在缺体时会平滑累加，直到体力自回足够一场战斗并立即扣除结算。
- **妥协点**：在线挂机时挂机时间持续累计在 `accumulatedSeconds` 中，若玩家体力上限很低且在线挂机很久，`accumulatedSeconds` 理论上可以很大，一旦通过道具/补给瞬间获得大量体力，会在单次 Tick 瞬间扣除并批量跑完对应场次。
- **待完善**：评估是否需要在线挂机最大单次结算秒数（如单 Tick 限制最多结算 N 秒）以防止极端帧时间跳跃或长休眠唤醒导致的大批量战斗突发性能峰值。

---

## 4. 长时在线挂机的掉落物与日志内存膨胀

- **现状**：`combat.idle.totalDrops` 是一个字典，同类可堆叠物品会累加数量；但挂机日志队列（`logs`）在线长期运行时，数组会持续增长。
- **妥协点**：`GameState.logs` 目前保留在顶层且本地持久化，上传云端时已做剥离（`delete uploadData.logs`），但本地长期连续挂机仍可能导致 `logs` 数组过长，增大本地 `localStorage` 写入负担。
- **待完善**：为本地 `logs` 增加上限滑动窗口（如保留最新 100 条）和环形缓冲，避免 `localStorage` 超限。

---

## 5. 战败重伤停止后的 UI 唤醒与交互引导

- **现状**：挂机遇到战败时，小队全员 `wounded = true, hp = 0`，`combat.idle` 自动置空为 `EMPTY_IDLE_STATE` 终止挂机。当前 UI 侧主要通过 Toast 或信息流日志提示。
- **妥协点**：状态机正确中断（防止重伤继续挂机送死），但用户体验上若玩家不在前台观察，可能发现挂机停了却不知具体是在哪一轮因为什么敌人战败。
- **待完善**：在 `combat-ui` 中增加「挂机中断告警与战败回顾弹窗」，直观展示战败小队状态、战败关卡与掉落总结，并提供一键跳转医疗所/治疗引导。

---

## 6. 云端同步覆盖的本地挂机保护提示与多端同步限制

- **现状**：云端拉取下载时，会弹出二次确认警告弹窗并重置本地挂机状态（`EMPTY_IDLE_STATE`）。
- **妥协点**：严格落实了 ADR-0020 决策（云端不保留挂机运行时），但对于多端玩家（如 PC 与手机切换），在一台设备开启的挂机，在另一台设备拉取云端时无法继承挂机进度。
- **待完善**：在文档与 UI 中明确向玩家沟通「挂机为本地单机行为，切端需手动在本地结清或重新挂机」。

---

## 7. `recoverStaminaByTime` 的浮点累积精度与整数口径

- **现状**：`stamina.ts` 的 `recoverStaminaByTime` 计算 `earned = elapsedSeconds / regenSeconds`，并在内部返回 `stamina: Math.min(maxStamina, current + earned)`，存储为浮点数；UI 与战斗扣除处通过 `getStamina`（读 `Math.floor(state.stamina)`）转为整数。
- **妥协点**：浮点数存储保证了每秒 Tick 的平滑自回（如 3 秒回 1 点时，每秒 +0.333），但在 `localStorage` 序列化与 Debug 观察时会看到类似 `99.33333333333333` 的浮点值。
- **待完善**：在持久化 `saveState` 或特定出口处对浮点体力做规范化（如保留 2 位小数或显式区分 `stamina` 与 `staminaFraction`），提升存档整洁度与调试可读性。

---

## 8. 关卡挂机与区域探索的体力竞争

- **现状**：荒野探索消耗体力（`encounterStaminaCost`），关卡挑战与挂机也消耗体力（`level.staminaCost`）。如果玩家一边在线探索触发遭遇战，一边后台挂机，两者共享同一体力池。
- **妥协点**：目前 UI 做了标签页互斥限制（在挂机时不允许探索，反之亦然），但底层 state 层面尚未做严格的互斥锁（Mutex）防并发。
- **待完善**：在状态机层面建立更清晰的「探索与挂机互斥」守卫规则，防止调用方或未来外部系统绕过 UI 产生并发体力扣减竞争。

---

## 9. `grantStamina` 的溢出策略尚无业务入口调用

- **现状**：`grantStamina(state, amount, allowOverflow = false)` 提供了 `allowOverflow` 参数，但目前游戏内尚未有体力药水、升级全额体力奖励等使用场景。
- **妥协点**：属于适度的预留（Speculative Generality），代码保持简洁纯函数。
- **待完善**：待道具使用或避难所/升级机制接入时，正式确立「常规恢复（受上限钳制） vs 补给道具（允许溢出上限）」的具体规则。

---

## 10. 关卡掉落物合并缺少装备实例去重或批量入背包语义

- **现状**：`mergeDrops` 仅处理基础材料/货币的累加（`Record<string, number>`），关卡挂机掉落中的装备掉落目前是通过 `addItemRewards` 逐件转入 `equipmentInventory`。
- **妥协点**：对于纯堆叠材料（矿石、残响、经验书）运行良好，但长时挂机产出大量同名低阶装备时可能塞满装备背包。
- **待完善**：在掉落与背包系统后续重构中引入装备自动分解/过滤策略（如挂机自动分解白装/绿装），避免装备背包膨胀。

---

## 建议处理顺序

1. **UI 与事件流统一（`combat-ui` 专项）**：统一挂机信息流生产者/消费者模型（#1），补全挂机战败中断告警弹窗（#5）。
2. **状态与存储整洁度**：持久化体力浮点数保留两位小数或分离小数部分（#7），本地日志增加滑动窗口上限（#4）。
3. **安全与互斥守卫**：底层状态机建立探索与挂机互斥（#8），单 Tick 挂机秒数结算上限防性能抖动（#3）。
4. **资源体系整合**：体力接入 `modifier` 支持装备/基建动态上限（#2），道具体力溢出机制接入（#9），挂机低阶装备自动分解过滤（#10）。
