# 工坊模块改造规范（workshop-rework）

Status: ready-for-agent

> 本规范由 wayfinder 地图（`.scratch/workshop-rework/map.md`）的 5 个决策 ticket 汇编而成，各章节标注决议来源，可回溯详情。**交付形态为规范，实施为独立 effort。**

## Problem Statement

工坊页面目前混杂三类职责，已偏离"工坊"的定义：

- **非生产功能占用**：页面顶部有"避难所生存补给发放"面板（快捷使用 4 种道具）与"梦魇入侵警报控制台"（出战防御）——前者与背包系统（物品详情 + 批量使用）能力重复，后者是防御事件而非生产行为。
- **数据重复维护**：配方表内的物品名称/描述与物品注册表（ITEMS_CONFIG）各自维护，存在漂移风险；手动配方（工坊）与自动配方（设施）存在 5 对数值完全一致的重复条目与 3 对近似条目，两套类型、两套字段命名（cost/reward vs input/output）。
- **无分类导航**：27 个配方平铺展示，玩家难以定位目标配方。
- **无批量合成**：每次只能合成 1 个，重复操作成本高（背包已有批量使用体验可对齐）。
- **展示数据硬编码**：补给配置、toast 文案、特殊配方渲染分支等硬编码在组件内，不可配置。
- **代码结构脆弱**：单文件约 15KB 混合多职责，后续需求增长将堆积技术债。

## Solution

将工坊重构为**纯生产/组装/合成区域**：

- 删除"补给发放"面板（背包已具备物品详情与批量使用能力）；
- 梦魇警报控制台迁至避难所运营页（后勤），工坊不再承担防御职责；
- 引入分类栏位：按产出物类别对齐背包 `ItemCategory`（道具/资源/碎片/装备）+ 补充类「建筑」，固定 5 类、无「全部」、空分类显示空态；
- 批量合成：配方卡片「合成」（x1）+「批量」（弹窗：数量滑条 + 消耗/产出预览），对齐背包批量使用体验；
- 数据单一真相源：配方模型统一（手动/自动共享类型），配方名称/描述从产出物完全推导，物品信息一律读取 ITEMS_CONFIG；
- 全数据可配置：分类定义、配方分类、批量上限计算等进入 data / 纯函数层，toast 文案集中常量；
- 代码结构：工坊组件拆分为独立子目录，纯逻辑收敛到 state 层可单测。

## User Stories

1. 作为生存者，我想在工坊按分类栏（道具/资源/装备/建筑）浏览可合成的配方，以便快速找到目标配方。
2. 作为生存者，我想看到未获得蓝图（图纸）的配方不出现在工坊列表中，以便列表只展示我能做的事。
3. 作为生存者，我想点「合成」按钮立即合成 1 个物品，以便快速制造。
4. 作为生存者，我想点「批量」按钮打开弹窗，用数量滑条选择数量并一次合成多个，以便批量生产（与背包批量使用体验一致）。
5. 作为生存者，我想在批量弹窗中看到消耗（cost×N）与产出（reward×N）的数量预览，以便确认投入产出后再合成。
6. 作为生存者，我想让稳定胶囊充能配方支持批量合成，以便一次性补充多次梦境充能。
7. 作为生存者，我想让温室扩建配方只能单次合成且不显示「批量」入口，以便避免误操作。
8. 作为生存者，我想让材料不足的配方仍然可见（显示缺口）但不可合成，以便我知道还缺什么材料。
9. 作为生存者，我想让无配方的分类显示空态提示（与背包一致），以便理解该分类暂无内容。
10. 作为生存者，我想在梦魇入侵时于后勤页（而非工坊）看到警报控制台并出战/部署炮塔防御，以便防御归位避难所运营。
11. 作为生存者，我想让工坊配方展示的物品名称/描述与背包完全一致，以便信息唯一、不困惑。
12. 作为开发者，我想让手动配方与自动配方共享同一类型定义与字段命名，以便消除重复维护。
13. 作为开发者，我想让配方的显示名/描述从产出物自动推导（无产物配方显式兜底），以便单一真相源。
14. 作为开发者，我想让分类定义、配方分类归属、批量上限等均为数据/纯函数驱动，以便数据驱动与可配置。
15. 作为开发者，我想让旧存档中被删除的自动配方 id 在加载时自动迁移映射，以便存档队列不丢失。
16. 作为开发者，我想让 toast 文案集中在常量文件，以便统一管理。
17. 作为开发者，我想让工坊组件拆分为独立子目录组件、纯逻辑进 state 层，以便后续扩展不堆积技术债。

## Implementation Decisions

（各决策详情与讨论见对应 ticket，以下为结论摘要。）

### 1. 配方数据模型统一（来源：配方去重与统一数据模型决策 + 调研手动/自动配方耦合）

- 共享基础类型 `Recipe`；`AutoRecipe` 类型删除并入。字段：`id`、`cost`、`reward`、`special?`、`capsuleTarget?`、`capsuleAmount?`、`blueprintId?`、`facilityId?`、`duration?`、`category?`（`ItemCategory | 'building'`）、`displayName?`。
- **删除 `name`/`description` 字段**：显示名 = 「合成 {reward 主产物名} ×N」，描述 = 主产物 `ITEMS_CONFIG.description`；无 reward 配方兜底：胶囊充能配方用 `capsuleTarget` 产物名，温室扩建用显式 `displayName`。
- 字段名统一 `cost/reward`（自动侧 `input/output` 迁移，波及设施队列状态层与设施卡片展示层）。
- 配置组织：双文件共享类型——手动配方表与自动配方表各自保留，类型定义收敛到一处。
- 分类字段（来源：工坊分类栏位设计）：默认从 reward 主产物 `ITEMS_CONFIG.category` 推导，无产物/需覆盖的配方显式声明。

### 2. 配方去重与存档兼容（来源：配方去重与统一数据模型决策）

- 5 对数值完全一致的重复配方：**仅保留工坊（手动）侧条目**，删除自动侧重复条目（`craft_rusted_spring`、`craft_nanite_slurry`、`craft_plasma_arc`、`craft_ration_deluxe`、`assemble_energy`）。
- 3 对刻意数值差的近似配方（以太合金 3/4、防御炮塔 4/3、防化口粮 含/不含 aether_pulp）：**双条目双数值保留**，不改经济平衡。
- 存档兼容：被删除的自动 id 在存档加载校验处做**一次性 id 迁移映射**（旧队列条目经映射后保留，未映射的 id 过滤）；`facilityId` 防呆校验保留。

### 3. 分类栏位（来源：工坊分类栏位设计）

- 维度：产出物类别对齐背包 `ItemCategory`（道具/资源/碎片/装备）+ 补充类「建筑」；充能配方归「道具」。
- 形态：固定 5 类、无「全部」；空分类（含因可见性过滤变空的分类）显示空态，判定基于可见配方；分类定义（id/标签/图标/排序）进 data 配置，可扩展。
- 分布核对（27 配方）：道具 12、资源 7、装备 7、碎片 0、建筑 1。

### 4. 配方可见性（来源：批量合成交互与特殊配方语义 · 修订）

- 配方可见 ⟺ 存在合成可能性：蓝图锁定（未持有 blueprintId）、温室扩建已达上限 → **从列表隐藏**（不渲染，移除现有"未解锁/锁图标/需要图纸"展示）；材料不足 → 仍显示但不可合成。
- 列表渲染前过滤，分类计数基于可见配方。

### 5. 批量合成（来源：批量合成交互与特殊配方语义）

- 交互：配方卡片双按钮「合成」（x1）+「批量」（打开弹窗）；弹窗含图标/名称、消耗×N、产出×N 预览、数量滑条（0~maxBatch）、合成按钮。
- 批量上限：`maxBatch = min(floor(库存/单次消耗))`（仅对可见配方计算）。
- 特殊配方语义：胶囊充能**可批量**（上限=材料上限）；温室扩建**禁批量**（强制 1、不显示「批量」入口）。
- 逻辑层：批量合成核心为纯函数原子操作（一次校验、扣料×N、产出×N），`GameContext.craftItem` 增加数量参数；材料不足整体拒绝，无部分成功。

### 6. 模块架构（来源：工坊模块架构与警报迁出）

- 新建 `src/components/workshop/` 子目录：页面容器、分类栏、配方卡片、批量弹窗、空态组件。
- 纯函数进 state 层（与现有合成更新同层）：分类推导、可见性过滤、批量上限计算；toast 文案集中常量文件。
- Context 接口：`craftItem` 增加数量参数；`supplyItem` 在工坊侧无调用点（接口保留给背包）；`defendDreamLeak` 接口不变。

### 7. 梦魇警报迁出（来源：工坊模块架构与警报迁出）

- 新建独立警报面板组件，挂载到**避难所运营页（后勤）顶部**；迁移现有警报 JSX（入侵者 HP 条、出战小队状态、炮塔/直接出战按钮）与相关引用。
- 全局警报横幅（非后勤页时显示）的跳转目标从工坊改为后勤页；工坊原警报区直接移除。

### 8. 补给面板删除（来源：地图 Notes + 用户决议）

- 删除"避难所生存补给发放"面板及组件内硬编码补给配置；`supplyItem` 工坊侧不再被调用；相关 toast 文案并入常量管理；原补给物品（口粮/能量补充剂等）仍可在背包查看详情与使用。

## Testing Decisions

- **好测试的标准**：只测外部行为——组件层验证用户可见的交互与状态结果，state 层验证状态更新结果，不测实现细节（不断言内部调用顺序、不 mock 无意义中间态）。
- **Seams**（已与用户确认，均为现有 seam）：
  1. **state 逻辑 seam**：state/workshop.ts 纯函数——批量合成原子性（扣料×N/产出×N）、特殊配方语义（胶囊充能批量、温室扩建强制 1）、材料不足整体拒绝、分类推导、可见性过滤、批量上限计算。先例：`expansion.test.tsx`、`GameContext.test.tsx` 对合成更新的测试。
  2. **UI 组件 seam**：workshop 子目录组件与警报面板——分类栏渲染/切换、空分类空态、可见性过滤（蓝图隐藏、材料不足显示但不可合成）、「合成」x1、「批量」弹窗（滑条上限=maxBatch、消耗/产出预览、调用合成）、警报面板渲染条件与防御调用。先例：`WorkshopTab.test.tsx`、`ItemDetailModal.test.tsx`（滑条交互）。组件测试需包裹 `GameProvider` + `ToastProvider`，以 localStorage 存档水合（仓库既定模式）。
  3. **迁移 seam**：persistence 层 id 迁移映射——被删自动 id → 保留 id 的映射、未映射 id 的过滤。先例：`heroes.test.ts`（mergeSavedState 存档合并测试）。
- 既有测试更新：`WorkshopTab.test.tsx` 的「蓝图锁定显示未解锁」断言改为「蓝图锁定配方隐藏」断言；警报相关断言随组件迁移调整。

## Out of Scope

- **实际代码实施**：本规范是交接物，实施为独立 effort（按本规范展开）。
- **梦魇入侵玩法本身**：数值、机制、掉落不做调整，仅迁移 UI 位置。
- **背包系统改动**：维持现状，仅作为工坊交互参照。
- **设施（自动配方）行为改动**：除字段名统一与 id 迁移映射外，自动产出逻辑与数值不变。
- **图鉴式未解锁配方提示**：本次决议为隐藏，若需"已锁定配方可见性提示"属新需求。
- **补给/道具使用能力**：不在工坊恢复，背包已覆盖。

## Further Notes

  4. 蓝图锁定展示分支（锁图标/未解锁/需要图纸）在配方卡片中的移除；
