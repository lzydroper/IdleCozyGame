# 12 — 时机/事件订阅接口（决策）

**Type:** grilling
**Status:** resolved
**Blocked by:** 08

## Question

Turn 的时机/事件订阅机制如何设计？（Turn 拥有主时机与事件总线；订阅方 Effect / Buff / Ability 本体 out of scope，本票只定 Turn 暴露的订阅契约。）

1. **订阅粒度**：订阅以「时机/事件 key + 单位 + 效果实例」为单位，还是更粗/更细？
2. **注册/注销**：API 形状（`register(时机|事件, 订阅者)` / `unregister(...)`）；战斗结束后订阅表是否自动清空？
3. **结算顺序**：同一时机/事件下多个订阅者按注册序（FIFO）还是逆序（LIFO）触发？是否需要可配置？
4. **同时机内再注册**：结算某时机时新注册到同一时机的订阅，是否延后到下一次该时机结算（Turn.md 已提此约束，是否确认）？
5. **触发上下文**：触发时向订阅者传入什么（当前回合归属单位、来源、目标、时机/事件 key）？

产出：Turn 的时机/事件订阅契约（注册表形状 + 结算顺序 + 上下文），供 Effect / Buff / Ability 后续接入。

## Answer

（HITL grilling，用户全部确认推荐方案）

- **D1 订阅粒度**：订阅键 = `(时机/事件 key, 单位 id | 全局)`——单位级时机按单位订阅、轮次级时机（轮次开始前/结束后）全局订阅；值 = 订阅者（效果实例/回调）列表。
- **D2 注册/注销**：`register(key, 订阅者)` / `unregister(key, 订阅者)`；战斗结束订阅表整体清空（每场战斗独立实例）。
- **D3 结算顺序**：FIFO（注册序）固定、不可配置；将来需要先后控制再引入显式优先级（现在不做）。
- **D4 同时机内再注册**：确认延后到下一次该时机结算，本轮迭代不触发（防无限循环）。
- **D5 触发上下文**：至少含 时机/事件 key、当前回合归属单位、来源、目标、战斗运行时引用（只读）；事件数据（伤害数值等）由派发方附带。
