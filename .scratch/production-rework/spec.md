# 产线改造：单任务批量生产 + 数据驱动设备注册

Status: ready-for-agent

## Problem Statement

产线（冶炼炉 / 组装台）目前使用 FIFO 队列模型：玩家必须**逐条把配方加入队列**，无法一次设定批量目标，生产管理繁琐且缺乏"批量投入"的经营感。同时产线代码存在两处结构性痛点：

1. **队列模型与目标不符**：队列语义是"多条目顺序执行"，但玩家真正想要的是"选定一种配方、设定生产数量、持续生产"。队列还引入了"队首材料不足自动暂停"等复杂分支，且中断移除只退单条原料，没有批量退款概念。
2. **新增设备种类困难**：设备类型 `smelter` / `assembler` 硬编码在类型定义、升级配置、产线 UI、驻守加成作用域、存档归一化多处；新增一种设备需要改动 5+ 处代码，而非加一条配置。

## Solution

把产线从"FIFO 队列"改为**单任务批量生产**模型，并做**数据驱动设备注册**架构重构：

- **单任务批量生产**：每台设备同时只跑一个「配方 × 批次」任务。玩家在设备上选择配方，用**滑条设定生产批次**（上限 = 当前材料可支撑的批次数，按驻守成本减免后计算），点击开始即**扣除全部材料**，随后逐批产出；生产完成自动回到待机。在线与离线持续推进。
- **中断退款**：取消任务时，已产出的批次保留，未开始 + 进行中批次**全额退还材料**（按折扣后单价），并在确认弹窗中预览退款。
- **数据驱动设备注册**：新增独立设备配置表（生产参数、升级、扩建、图标内聚），`FacilityType` 由配置推导；`SHELTER_UPGRADES` 收敛为纯全局升级；升级机制同步泛化（配置源分派）。新增设备 = 配置表一条 + 自动配方一条，其余自动生效。
- **UI（变体 B）**：设备卡只做状态摘要（待机/生产中 + 进度 + 已产/目标 + 取消），**驻守按钮入口保留**；「生产」走滑条弹窗（对齐工坊批量合成心智）；「取消」走确认弹窗带退款预览。

## User Stories

1. 作为玩家，我想在设备上选择配方并用滑条设定生产批次数量，以便批量生产而无需逐条入队。
2. 作为玩家，我想看到滑条上限 = 当前材料可支撑的最大批次数（含驻守成本减免），以便知道最多能生产多少。
3. 作为玩家，我想在开始生产前看到消耗 ×N 与产出 ×N 预览（每批产出含驻守产量加成），以便确认投入产出。
4. 作为玩家，我想点击「开始生产」后立即扣除全部材料，以便一次性投入、无需分批支付。
5. 作为玩家，我想看到生产进度（当前批进度条、"已产 X / 目标 N 批"、当前批剩余秒、总剩余时间），以便了解完成情况。
6. 作为玩家，我想生产完成后设备自动回到待机，以便继续安排下一个任务。
7. 作为玩家，我想取消进行中的任务并看到退款预览（已产出保留、退还剩余材料数量），以便灵活调整生产计划。
8. 作为玩家，我想驻守英雄加成（生产速度 / 额外产出 / 原料减免）实时作用于任务计算与展示，以便后勤指派真正影响产线。
9. 作为玩家，我想扩建后的每台设备都能独立安排任务、各自推进，以便多台设备并行生产。
10. 作为玩家，我想离线时任务持续推进，回归后已完成批次入账、未完成批次保留进度，以便获得挂机收益。
11. 作为玩家，我想设备卡保留驻守按钮（指派 / 更换 / 解除英雄），以便继续管理后勤指派。
12. 作为玩家，我想从设备卡发起生产（弹窗滑条），以便与工坊批量合成的心智一致。
13. 作为玩家，我想开始生产 / 取消任务有明确的 toast 与日志反馈，以便确认操作生效。
14. 作为玩家，我想生产 / 取消操作的材料扣减与退还准确（含驻守减免，退款不赚差价），以便经济系统公平。
15. 作为玩家，我想旧存档（含队列）加载后无异常、队列被自动清空，以便升级后平滑过渡。
16. 作为玩家，我想设备升级 / 扩建仍然可用（升级耗时机制保留、数据迁移到新配置表），以便与基建升级语义一致。
17. 作为玩家，我想材料不足时无法开始新任务（滑条上限为 0 或按钮禁用），以便避免无效操作。
18. 作为开发者，我想新增设备种类时只需添加设备配置一条 + 自动配方一条，以便低成本扩展新产线。
19. 作为开发者，我想产线逻辑以纯函数状态机呈现、可单测覆盖，以便降低回归风险。

## Implementation Decisions

### 任务状态机（源自 01 决议，type shape 内联）

`AutomationFacility` 移除 `queue: string[]` 与 `active?: boolean`，改为单任务字段：

```
interface AutomationFacility {
  id: string; name: string; level: number;
  recipeId: string | null;   // null = 待机
  targetCount: number;       // 目标批次数（开始生产时扣 targetCount × 每批折扣成本）
  completedCount: number;    // 已完成批次数
  timeLeft: number;          // 当前批剩余秒（推进真相）
  currentProgress: number;   // 当前批进度 0-100（UI 展示，由 timeLeft 推导）
}
```

- **计时模型**：逐秒 `timeLeft` 推进（沿用现有推进模式）——在线按 elapsedSeconds 推进、离线一次性传总秒数；批次耗时 = `getActualDuration`（设备等级 + 驻守速度加成）。
- **扣料与退款**：
  - 开始生产：校验 `targetCount × 每批折扣成本` 足够 → 扣全部（驻守原料减免按 `max(1, floor(成本 × (1 - costReduction)))` 折扣）→ 置任务。
  - 每完成一批：`completedCount + 1`、reward 入账（产量加成 `floor(reward × (1 + yield))`）；`completedCount >= targetCount` 时任务结束回待机。
  - 取消任务：退款 = `(targetCount - completedCount) × 每批折扣成本`（未开始 + 进行中批次全额退，与 timeLeft 解耦）。
  - 删除"队首材料不足自动暂停"逻辑（材料已扣，不存在生产中缺料）。
- **状态**：待机 ↔ 任务进行中；移除启停开关，只有「开始任务 / 取消任务」。

### 数据驱动设备注册（源自 04 决议）

- 新建独立设备配置表：每类设备内聚 名称 / 图标 / 升级等级表（复用 UpgradeLevel，含耗时）/ 扩建（maxUnits、costs、durations）；`FacilityType = keyof typeof 设备配置表`（用 `satisfies` 保留字面量推导，类型安全不丢）。
- `SHELTER_UPGRADES` 收敛为纯全局升级（蓄电池 / 发电机 / 回收站 / 温室扩展坞）。
- **升级机制同步泛化**：升级 / 扩建入口做配置源分派——设备类型读设备配置表，全局类型读 SHELTER_UPGRADES；`UpgradeStatType` 的设施部分由 `FacilityType` 推导。
- **UI 泛化**：产线设备卡与基建升级卡按设备配置表遍历渲染（删除冶炼炉 / 组装台硬编码导出）；图标注册表兼容两表。
- **存档**：设施归一化按设备配置表 key 遍历，未知类型丢弃；旧队列字段一次性清空（不转换）。

### UI 交互（源自 03 决议，变体 B 获胜）

- **设备卡 = 状态摘要**：待机态（设备名 / 等级 / 驻守按钮与加成摘要 / 「＋ 生产」按钮）；生产中态（配方名、当前批进度条、"已产 X / 目标 N 批"、当前批剩余、总剩余、每批产出含加成、「取消任务」）。
- **「生产」弹窗**：对齐工坊批量合成——配方选择 + 批次滑条（上限 = floor(材料 / 每批折扣成本)）+ 消耗 / 产出预览 +「开始生产（扣除全部材料）」。
- **「取消」确认弹窗**：展示退款预览（"已产出的 X 批将保留，将退还：材料 ×Y"）。
- **驻守入口保留**：沿用现有指派弹窗，加成实时作用于任务计算与展示。
- 多台设备各一张独立卡；基建 tab（升级 / 扩建）不变，仅数据源迁移。

### 移除

- `enqueueRecipe` / `removeQueueEntry` / `setFacilityActive` 相关纯函数、context 方法与 UI（队列区）。

## Testing Decisions

**好测试的标准**：只测外部行为——状态机纯函数给输入断言输出（扣料数量、推进后的字段、退款数量、完成判定）；组件测试断言渲染与交互结果。不测实现细节（内部辅助函数、局部状态）。

**主 seam：`state/facility.ts` 纯函数状态机**（扩展 `facility.test.ts`）：
- 开始任务：扣全部材料（含成本减免）、置任务字段、材料不足 / 已在生产中 / 未知配方拒绝
- 推进：逐批 `completedCount + 1` 与入账、最后一批完成回待机、进度字段正确
- 取消：退款 = (targetCount − completedCount) × 折扣单价、任务清空、已产出保留
- 加成：速度缩短耗时、产量 floor 入账、成本减免扣 / 退同价
- 多台设备独立任务并行

**辅助 seam 1：在线 tick**（扩展 `tick.test.ts`）——`applyTick` 按 elapsedSeconds 推进任务、任务与基建升级（0019）共存互不干扰。

**辅助 seam 2：离线结算**（扩展 `GameContext.test.tsx` 离线部分）——离线按总秒数推进任务：已完成批次入账、未完成保留 `timeLeft`；离线回归与升级结算（先应用升级再结算产出）顺序正确。

**辅助 seam 3：UI 组件**（扩展 `FacilityCard.test.tsx` / `ShelterTab.test.tsx`）——设备卡待机 / 生产中渲染、生产弹窗滑条上限与预览、取消确认退款预览、驻守按钮保留可打开指派弹窗。

**先例**：现有 `facility.test.ts`（纯函数状态机）、`tick.test.ts`（applyTick）、`GameContext.test.tsx`（离线结算）、`FacilityCard.test.tsx`（组件）。

## Out of Scope

- **队列功能的任何保留**：旧队列不兼容保留，旧存档 queue 一次性清空。
- **「持续生产」模式**：已否决（与"开始扣全部材料"矛盾）。
- **产量加成余数累计**：沿用 floor 公式，reward=1 时小数值加成不生效属已知接受行为。
- **新增设备种类本身**：本次只做"可配置扩展"的架构，不新增冶炼炉 / 组装台之外的设备。
- **工坊手动合成**：手动配方与合成逻辑不动。
- **0019 升级耗时机制本体**：不做行为改动，仅将设备升级 / 扩建的数据源迁移到新配置表。
